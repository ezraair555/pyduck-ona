# pyduck-ona v0.3 API Contract (Draft)

This defines a uniform verb system so `pyduck-ona` and `pyduck-janitor`
compose as one analysis stack.

## 1) Core Principles

1. Relation-first runtime:
- Default return type is `duckdb.DuckDBPyRelation`.
- Materialization is explicit (`.df()`/`collect()`), never implicit in core verbs.

2. One canonical entity key:
- All employee-level outputs expose `entity_id`.
- Compatibility aliases (`employee_id`, `node_id`, `manager_id`) can be added only at export.

3. Stable verb grammar:
- Verb names are action-first and domain-scoped.
- No overloaded meaning across modules.

## 2) Verb Taxonomy

Use five families with strict prefixes:

1. `prep_*`
- Data prep and validation.
- Examples: `prep_load_hris`, `prep_validate_keys`, `prep_filter_noise`.

2. `graph_*`
- Network construction and centrality/community metrics.
- Examples: `graph_edges`, `graph_betweenness`, `graph_pagerank`, `graph_louvain`.

3. `temporal_*`
- Time-window, drift, mobility, and trend computations.
- Examples: `temporal_metrics`, `temporal_evolution`, `temporal_change_detection`.

4. `model_*`
- Statistical and predictive models.
- Examples: `model_ols`, `model_logistic`, `model_chi_square`, `model_markov`.

5. `report_*`
- Packaging outputs for consumers.
- Examples: `report_scorecard`, `report_alerts`, `report_export_table`.

## 3) Uniform Method Signature

Every public verb should follow this envelope:

```python
def <family>_<verb>(
    self,
    *,
    source: duckdb.DuckDBPyRelation | str | None = None,
    key: str = "entity_id",
    as_pandas: bool = False,
    output: str | None = None,
    **kwargs,
) -> duckdb.DuckDBPyRelation | pd.DataFrame:
    ...
```

Rules:
- `source` accepts relation or registered table name.
- `key` declares the entity join key in output.
- `as_pandas=False` by default.
- `output` optionally registers a named table/view.

## 4) Output Contract

Each verb documents:

1. Input schema (required columns and types).
2. Output schema (column names/types).
3. Determinism controls (`seed`, ordering).
4. Null behavior.
5. Scale posture (in-memory vs relation-only).

Minimum metadata for docs/tests:

```yaml
verb: graph_pagerank
input:
  required: [source_col, target_col]
output:
  key: entity_id
  columns:
    - entity_id: string
    - score: float
deterministic:
  seed: null
```

## 5) Bridge Contract (`pyduck-janitor` <-> `pyduck-ona`)

Required adapters:

1. `DuckONA.from_janitor(dj, hris_table="hris")`
- Reuse live DuckDB connection.
- Register janitor relation as HRIS table.

2. `DuckJanitor.to_ona(hris_table="hris")` (optional reciprocal adapter)
- Thin wrapper calling `DuckONA.from_janitor(self, ...)`.

## 6) Compatibility Plan

1. Keep existing methods in v0.3.
2. Add prefixed aliases (`graph_pagerank` -> current `pagerank`).
3. Emit deprecation warnings in v0.4 for non-uniform names.
4. Remove old names in v1.0 after migration guide adoption.

## 7) Non-negotiable Safety/Quality Gates

1. SQL values parameterized; no scalar string interpolation in public methods.
2. Identifier quoting centralized.
3. New verb requires:
- Input schema test
- Output schema test
- Regression test for edge/null case
- Performance smoke for >100k rows where applicable

## 8) Golden Flows (Must Stay Green)

1. Compensation equity:
- `prep_*` -> `graph_*` -> `model_ols` -> `report_scorecard`

2. Attrition risk:
- `prep_*` -> `temporal_*` -> `model_logistic` -> `report_alerts`

3. Org redesign impact:
- `prep_*` -> `graph_*` + `temporal_*` -> `report_scorecard`
